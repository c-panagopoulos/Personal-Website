# How this portfolio's assistant works

This is the retrieval-augmented assistant (also known as RAG) answering your questions right now, on this
site. It's the same pattern as Hermes, pointed at my own about-me notes and project notes instead of a
support knowledge base.

Ingestion: every markdown file in the content folder (my about-me notes, and my project and
homelab writeups) gets split into chunks. Chunking respects markdown headings as hard boundaries, so a
section never gets merged with an unrelated neighboring section, and within a section it splits on sentence
boundaries so a chunk is never cut mid-sentence, with a bit of word-level overlap carried into the next
chunk for continuity.

Embedding: each chunk is turned into a vector using a local Ollama model (`nomic-embed-text`), not a hosted
API — the embedding step never leaves my own hardware. Those vectors are stored in PostgreSQL using the
pgvector extension, one row per chunk, alongside the chunk's source file and raw text.

Retrieval: when you ask a question, the question itself gets embedded the same way, then compared against
every stored chunk using cosine similarity. The top matches above a minimum similarity score are pulled
back — if nothing scores high enough, none are returned, rather than forcing in a weak, irrelevant match.

Generation: those matched chunks are injected into the system prompt as context, along with an instruction
to answer only from that context and say plainly when something isn't indexed rather than guessing. The
last few turns of the current conversation are included too, so a follow-up question can lean on what was
already asked. The actual answer is generated by Groq (fast hosted inference), falling back automatically
to Gemini if Groq's daily quota is exhausted, and streamed back token by token over Server-Sent Events, so
it appears in the chat as it's written instead of all at once. The source chips shown above an answer are
exactly the files that context came from — nothing is hidden or summarized away.

Q: What's the weakest part of this architecture, this specific retrieval assistant's architecture?
A: Retrieval only embeds the current question's text when picking chunks, not the full back-and-forth, so a
follow-up that leans heavily on earlier context can occasionally pull weaker matches than a fully
self-contained question would. This assistant also has no automated test suite covering it, unlike the
fact-check pass TapStudy runs on its own AI-generated insights, I've relied on manually re-testing each
change to this assistant by hand instead. If you're asking about weaknesses, flaws, or downsides of how
this portfolio's own retrieval-augmented assistant is built, this is the honest answer.
